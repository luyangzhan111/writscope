# S3 v6 c004 失败的离线归因

本分析只读取已保存的 v6 请求/原始响应与公开案例材料；不改真实记录、不读私有标签、不调用 provider。

## 观察到的内容

1. v6 新契约解决了上一轮续答的**结构接口**问题：本轮没有 lookup continuation，但同轮输出中的条件使用 `candidate_sha256`、`patch`，格式可通过 v4 条件schema。
2. 同一条件把当前候选摘要标为 `satisfied`，但模型从未请求回查隐藏的 e002 原文。该摘要只能视为未被自主回查证实的模型主张，不能据此判定回查成功或授权成立。
3. e005 提案的授权对象是 `/api/v1/profile` 的 `status` 字段；其 `constraint_refs` 同时包含 `c_v1_profile_status`、`c_minimal_change_no_new_api` 和 `c_page_local_mapping`。后两项的状态主体字段是 `state`，与授权主体 `status` 不同。scope kernel 因两条引用的范围不匹配拒绝整个批次，首错停止正确执行。
4. e001与e004的候选约束都在各自事件接受；e001还同时保留了客户端映射任务背景。它们是否应作为当前授权的约束引用、以及模型应如何筛选字段/作用域，需先按现有生命周期与scope契约作离线规则对照。本记录不把内核拒绝归因成内核错误，也不擅自删除约束引用或改写响应。

## 结论及后续

- 本次真实回查状态为 `not_exercised`；无有效终点，开发与完整S3退出均不满足。
- 新v4 schema消除了“条件类型名/事件ID冒充artifact ID”的结构错误，但没有解决条件是否经历史证据验证、也没有解决授权与约束引用的scope对齐。
- 下一步只做离线契约诊断：明确哪些活动约束能被某一授权引用、subject字段和作用域检查的准入条件、以及缺少回查时如何保留不确定性。用原始响应和合成控制核对，不修改本轮请求/响应/分数。
- 任何新真实试跑必须另立计划并取得新预算与精确材料外发授权；本次3元授权已用。独立审核者仍缺，完整S3不得签收。
