# M2 计划：两种完整上下文基线与可复现评测流程

日期：2026-10-20。状态：**M2a P0–P5 已按本计划落地并本地验证；M2b 真实接通仍是计划、未运行。** 实际结果见 [M2a 验收](m2a-review.md)。M2 对应 [总计划](implementation-plan.md) 的 S2，不增加新的研究阶段。

## 1. 建议与依据

下一里程碑先把 M1 的样例、输入包和影响证据接到两种完整上下文复核方法，并形成独立评分、完整日志和可复现报告。先完成无密钥的工程验收，再在模型与预算确定后做少量真实调用接通验证。

这是当前最直接的推进路径：M1 已有固定代码、三种授权历史和执行证据；尚缺方法输出及其验证流程。强基线会提供后续增量状态方法的比较对象，也能及早暴露案例措辞、输出契约和评分口径的问题。此时增加 Web UI、数据库、多 Agent、IDE 插件或大量案例，不能解决这项主要缺口。

开源定位暂定为“可复现的编码兼容性与授权范围研究原型”。下一次交付应让贡献者无需密钥就能理解案例、运行测试和查看报告，并能明确区分真实模型结果与离线流程测试。

实施前核对到：本地 main 原先无提交、无远程；M1 已保存成功执行记录和 34 项测试通过摘要。M2a 已建立本地 M1 基点提交，补齐现有固定输入包的契约、两基线及离线记录；无远程。见 [M1 验收](m1-review.md)和 [M2a 验收](m2a-review.md)。

## 2. 范围与完成定义

M2 第一部分（M2a）仅使用现有三个历史、实验 A 的 verified_impact 证据包和最终决策点。两种方法都获得完整历史、初始代码、同一候选与同一实际影响证据，不向方法开放 shell、Python 或任意文件读取。

计划形成以下完整流程：

```text
M1 公开输入包 → 验证/解析工件 → 直接复核或清单复核
                                 ↓
                         统一调用适配与原始输出
                                 ↓
                      结果结构和证据引用校验
                                 ↓
                    保存结果 → 独立评测器读取参考标签
                                 ↓
                      三轴结果、失败和成本报告
```

M2a 完成只表示流程与方法接口可运行，不能表示模型理解授权或某方法更准确。真实接通验证为 M2b，需另外满足用户的模型调用授权、可用模型/凭据及预算条件；缺失这些不阻塞 M2a。

M2 不实现增量状态更新器、自动修复 Agent、30 例数据集、实验 B 执行工具或一般不可信代码沙箱。清单基线使用临时约束/授权结构；持续更新、撤销关系回放留 M3。

## 4. 关键设计约束

### 输入与证据

- 方法只接收经过校验的内存输入；复核方法模块不接收项目根目录或 evaluator_only 路径。
- 所有 artifact_id 必须解析到白名单工件；公共代码和影响事实的实际内容进入方法输入，不能让一个方法额外看到隐藏测试日志。
- 测试最终构造的请求，而不只是导出的文件目录。私有哨兵、标签、兼容参考补丁和未来事件不得出现在请求中。
- 模型引用的 constraint/authorization ID 必须能解析到输入或其显式声明的派生条目；不能仅验证字符串非空。直接基线不强制执行清单重建流程，但任何输出引用都必须有定义和来源。
- 结构合法但语义判断错误，保留为判断错误；程序不得读取参考答案“纠正”输出。程序也不能凭引用格式正确宣称其语义支持授权。

### 两种基线的公平性

- full_direct：读取完整输入，直接输出三轴结论与证据。
- full_checklist：先整理当前约束/授权，再核对 API 版本、对象、操作、条件和撤销/替代关系，最后输出相同三轴结论。
- 首版均计划单次调用。清单临时结构与未来 M3 状态条目尽量一致；不提前实现持久化状态系统，也不为直接基线增加相同清单要求。
- 同一基础模型、配置与工具权限；输出空间须能容纳清单。记录实际耗费，不能把等配置误称为等总预算。

### Mock 与评分器

- mock 用开发者显式指定的响应脚本测试流程，不根据 case_id、授权关键词或参考标签选择“正确答案”。它不是授权算法。
- 测试响应应包含正确、错误和无效结构等情形；mock 三例全对没有研究意义。
- 参考标签只在结果保存后的评分步骤读取。应有回归测试：改变参考标签只改变评分，不改变方法请求或响应；案例 ID 不充当答案查表键。
- 三个历史是一个开发场景的变体；不将它们的高分、重复采样或现有诊断配对当作独立泛化证据。

### 成本与失败

- 每次调用记录请求/响应引用、配置和提示词哈希、耗时、可用用量、费用来源及错误；失败后重试是独立 attempt，保留原记录。
- mock 实际模型调用/账单为零；测试中注入的 token/费用单独标记为合成测试数据，不混进实测。
- 缺失实际用量或费用是 unknown；没有可执行预算控制时，不启动需要预算保障的真实调用。
- 为 M3 保留 extract/update/lookup/review 阶段字段即可，不提前实现这些组件；后续所有维护费用仍须计入。

## 6. M2a 验收清单

- 现有 M1 行为不回退；若代码发生变化，重新生成新运行记录，旧报告不覆盖。
- 两方法 × 三历史能完成离线端到端流程，每次有独立运行身份、请求、输出、校验与评分记录。
- 最终请求具备同等完整证据，私有材料/未来事件未泄漏；引用与哈希失败被明确记录。
- mock 覆盖有效错误答案、非法 JSON/标签组合、来源错误、用量缺失、超时及有界重试；验收看行为覆盖，不预先追求测试数量。
- 评分分开显示影响、授权和最终决策；方法失败不会静默消失，修改标签不影响被测输出。
- 报告可从保存记录重算；mock/实测身份明确，费用缺失不当零，失败耗费不漏计。
- 无密钥命令与贡献说明齐备；Windows 为现有验证环境，Linux 作为待验证目标。CI 配置写完不等于 CI 已在远程成功运行。

## 7. 后续真实接通与研究顺序

M2b 在用户明确授权真实调用并确定模型/provider、可用凭据、费用上限、并发/超时/重试限制后进行。建议先用一个模型跑两个方法和三个历史，每组合一次，即 6 个计划复核任务；重试调用额外受预算约束。这只是接口接通与输出行为检查，不是正式比较，不能据此宣称强弱。

接通时只实现所选 provider 的一个真实后端，复用 M2a 的输入、校验、记录和预算边界；不同时接入多个供应商。先验证实际请求能限额、用量能落盘、错误可追踪，再执行这 6 个任务。

每次试跑前保存提示词、配置、代码和数据版本。若结果不符合参考，保存原输出并区分契约、提示词、接口或语义错误；修订后的再跑属于新的开发运行，不挑最好的一次作成绩。若模型未就绪，M2a 验收后仍可按原计划推进 M3 的离线状态开发。

之后按原研究路线推进：

1. **M3 增量状态组件：** 在已有强基线和共同记录上实现逐事件提取、局部例外、撤销/重授权和可重放状态；用定向案例验收，不因三个简单历史全对就主张方法增益。
2. **M4 首轮开发评测：** 完成 30 实例编制与核验，冻结参数/重复次数/比较预算/容忍阈值，分 A/B 轨报告；A 轨先行，B 轨在执行权限边界满足后运行。
3. **独立验证：** 另建未用于提示词调试的任务家族，才讨论泛化、长历史及实际编码 Agent 接入。

## 8. 开源发布与待决事项

M2a 可作为研究预览版的候选交付，但“可发布”与“执行发布”是两个独立动作，当前没有发布授权，也不新增开源许可证。

发布前需由作者确定许可证、仓库地址与公开范围；核对样例来源、日志中的本机路径/敏感配置以及第三方复用情况。原始研究记录保持不变，需要对外展示时生成单独的可移植/脱敏副本，并保留与原记录的对应关系，不能静默改写原始证据。

开源首屏应说明能做什么、不能做什么、如何无密钥复现、怎样贡献一个案例，并链接实际证据。不要在没有实测前放准确率/成本优势宣传、未通过的 CI 徽章或“生产可用”的声明。

| 待决事项 | 阻塞哪一步 |
| --- | --- |
| 下一轮是否进入 M2a 实现 | 已解决：用户授权且已实施 P0–P5 |
| 模型/provider、凭据与预算 | M2b 真实调用；不阻塞 M2a |
| 正式比较配置、重复数和质量/成本门槛 | M4 比较；不以六任务接通验证代替 |
| 许可证、远程地址与发布范围 | 实际开源发布；不阻塞本地 M2a 开发 |

M2a 实现与验证见 [M2a 验收](m2a-review.md)。本地离线流程结果不等于模型实验或性能结果。
