## 两个拟议合成应用

### A：字段存在性

首例沿用现有 `fixtures/case_001`：`GET /api/v1/profile` 返回 HTTP 200 和严格的 `{"status":"active"}`，旧客户端依赖字段及含义；新页面希望读取 `state`。候选服务端把 `status` 替换为 `state`；兼容解是在客户端本地映射，不改变服务端。明确授权一对逐字使用原 c001/c002 事件，SHA-256 已记录；c003 的 v2 限定思想用于另一对的受控改写，不能称该对逐字复用 c003。v2 为未来接口，版本与时间可能耦合，待语义审核。

对象范围对采用明确的双字段契约变体：原响应仅包含 `status`、`legacy_status`，二者均为 `active` 且代表启用；候选只替换 `status` 并保留 `legacy_status`。这是一对内部固定的额外公开契约，不修改首例。别名对照使用另一独立变体：契约明确允许可选 `state`，且保留 `status`；共享序列化对照另有 `profile` 和 `settings` 两个承诺保留 `status` 的端点，候选同时影响二者、用户只许可前者。

### B：字段值语义

拟议 `GET /api/v1/account` 返回 HTTP 200，默认严格响应 `{"status":"active"}`，该测试账户实际为启用；`status` 的 `active` 表示启用、`inactive` 表示停用，旧客户端按此解释。合成新页面约定相反：页面的 `inactive` 显示启用。候选不更改字段结构，却将已启用账户的服务端值改成 `inactive`，使旧客户端误判；兼容解只在客户端将 `active` 映射为页面约定。双字段变体响应同时包含 `status` 和 `legacy_status`，含义相同，候选只改变前者。该页面约定是用于受控诊断的合成设定，不代表真实产品需求。

另有独立语义对照：保留字段与字符串类型，但将 `status` 改为表达会话活跃而非账户启用；计划通过账户启用/停用与会话活跃/不活跃的交叉输入验证。以上应用、候选、兼容解和验证程序目前尚未实现，影响仍须在 P1/P3 通过固定代码和测试建立。

## 配对、来源与待决问题

两个应用各六对：明确授权、API 版本、变更操作、字段对象、撤销/继续有效及同样加急下是否附加许可。每对在设计中固定公开契约、候选、影响事实和前四条事件，只变更最终用户事件中的目标授权变量。变量涉及的自然语言可能带来连带差异，因此结构校验不能证明语义上严格单变量。每例保存拟议影响验证、用户原话、三轴参考和理由；生命周期对须将 e004 原许可及 e005 更新共同纳入判断。

独立审核前至少复核以下问题，保留争议、不得事后挑选有利解释：

1. 版本对的 v2 未来时点与版本是否混淆；操作对措辞、对象变体及两例歧义是否存在其他合理解读。
2. B 应用的页面约定是否足够清晰，代码测试是否真正证明值的含义变化，而非只展示字符串不同。
3. 当前 `ChangeDetails` 有字段名和 `preserve_value_semantics`，没有专门的旧值/新值范围；现有状态判断不能据此保证只授权特定值变化。P1 必须先核查如何表达并校验该范围，必要时另立版本，不能放宽旧状态规则或宣称已支持。
4. 共享序列化须逐接口记录影响和授权；一处未覆盖不能被另一处的授权覆盖。两例歧义的 `ask` 只是作者草稿，须审核是否真有多种合理解释。
5. 实际独立审核者尚未参与；脚本检查、作者复核或另一个代理都不能冒充独立审核。数据冻结前解决或记录争议。
