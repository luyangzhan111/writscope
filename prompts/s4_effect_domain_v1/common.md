EFFECT DOMAIN AND NON-AUTHORITATIVE CONTEXT v1

This later contract replaces the earlier exact final envelope {kind,payload} with {kind,payload,task_context}. It also extends the earlier extraction operation list with record_context and requires effect_domain on server authorization mutations. The supplied output_schema defines the complete current shape; all other prior source, state, lookup and checklist rules remain applicable.

This version separates API authorization from task context. Every authorization object refers to the HTTP API response body on the server. A client-local mapping or implementation permission belongs in the separate task_context channel, never in derived_items with kind=authorization, a server grant, or a positive per-impact authorization citation. Negative judgments may cite client-local text as evidence that server permission is absent.

For a server permission, select a minimal, exact user quote explicitly naming the server/API effect and permission. Do not cite a whole paragraph mixing client mapping and server changes; select the exact server clause. A model-written effect_domain=server_api is not evidence by itself. The runtime conservatively rejects client/mixed mapping evidence and abstains on unrecognized, negated, conditional or uncertain surface forms. A successful cue check only recognizes a bounded surface form; it is not proof of intent, permission, preserved qualifications or general semantic correctness. Never relabel an unresolved server permission as task background just to pass validation.

Every final result has exactly kind=final, payload and task_context. task_context is a list of exact user source_ref objects (event_id, quote) plus verification_refs using supplied public artifact IDs, or an empty list. It is non-authoritative and does not waive any constraint. All methods keep the same original evidence, complete terminal history and bounded lookup permissions. Do not use reference labels or any author's expected state.
